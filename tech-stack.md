# Tech Stack

## Overview

TypeScript monorepo on Bun: React + Vite frontend on Vercel, Express API running on Bun (with in-process background jobs) in Docker on Koyeb, PostgreSQL on Neon, Resend for email, and Claude for AI. All hosting uses free tiers (portfolio project).

## Repository

Bun workspaces (`bun.lock` at the root):

- `apps/web` (`@helpdesk/web`) — frontend
- `apps/api` (`@helpdesk/api`) — API and background jobs
- `packages/shared` (`@helpdesk/shared`) — shared types and Zod schemas, imported as TypeScript source via `workspace:*`

Root scripts:

| Command | Runs |
|---|---|
| `bun run dev` | API (`bun --watch`) and Vite dev server |
| `bun run typecheck` | `tsc` in every workspace |
| `bun run lint` | `oxlint --deny-warnings` in every workspace (warnings fail the run) |
| `bun run format` / `format:check` | Prettier write / check across the repo (Markdown excluded) |
| `bun run build` | Frontend production build |

## Frontend (`apps/web`)

| Concern | Choice |
|---|---|
| Framework | React + Vite + TypeScript |
| Routing | React Router 8 in data mode; route table in `src/routes.tsx`, browser router created in `App` |
| Data fetching | axios for the HTTP call, TanStack Query for server state — two jobs, two libraries. Never native `fetch`. Query client in `src/lib/query-client.ts`, no retries on 4xx |
| Tables | shadcn `Table`, with a visually hidden `<caption>`. Status and role read as words in a badge; the colour only seconds them, so nothing is lost by a reader who cannot tell two badges apart |
| Dialog forms | shadcn `Dialog`, same react-hook-form + zod pattern as login. Closing by any route resets the form and the mutation, so a half-typed password never waits in a closed dialog. A 409 is set on the field it names with `setError` and focused — unlike login, the admin needs to know which value to change. After a create, the list is invalidated rather than patched, and a polite live region, always rendered, announces it |
| New-password fields | `autoComplete="new-password"` on any password an admin sets for someone else. Without it a password manager fills in the admin's own saved password and the account is created with it |
| Row actions | One pencil per row, named for its user (`Edit Gil Agent`) since every row's looks the same. It opens an edit dialog: name and email filled in, an optional new password (blank keeps it), and an Access section with Deactivate or Reactivate. Only what changed is sent. Deactivation sits behind an `AlertDialog` held open until the API answers, so a failure shows beside its button; reactivation only restores and does not ask. Where the pencil and Deactivate appear is decided by the shared `authorise()` the API enforces, so the page never offers what the API would refuse; rows the viewer cannot touch say "Protected" or show a dash, with a screen-reader reason |
| Ticket list | `/tickets`: a shadcn `Table` with an Assignee column (the name, or Unassigned) and Status, Category and Assignee filters — Anyone, Assigned to me, Unassigned, sent as the API's `me` and `none` — a Needs agent filter (All, Needs agent, No agent needed, sent as `needsAgent=true` or `false`; 6.7), a Sort by select (latest/oldest activity, newest/oldest ticket) and a pagination bar carrying rows per page (5/10/20/50). Filters, sort, page and page size live in the URL, so a filtered list is linkable, survives a reload, and the back button walks the choices; a URL that will not parse falls back to the default list rather than an error nobody can act on. Any change but paging returns to page 1. The query and the viewer's id are both part of the TanStack Query key, so a page already seen returns from cache and the previous page stays on screen while the next loads, while `assignee=me` — a different list for each person — cannot be served to the next viewer. Signing in and out already clear the cache; the key is what keeps that true if some later way of changing user skips it The Needs agent column shows the reason as its badge (refund approval, AI could not answer, sender not verified, AI reply limit reached), from one label list in `apps/web/src/lib/escalation.ts` shared with the ticket page; a flag with no reason reads Yes |
| Ticket detail | `/tickets/:id`, opened from a subject in the list: subject, student, the summary and the timestamps above the thread. The summary sits in a region named "AI summary" with an AI badge (6.5): only the AI writes one, so an agent reads it as the model's reading of the thread, not a person's. The category is the editable select in the controls, which replaced the read-only badges, so it gets no badge of its own; the database does not record whether the AI or an agent set it, so it is not labelled AI. Messages read oldest first, each naming its author in words — the student, `AI assistant`, or the agent who replied — with a role badge; tint and indentation only second that, so none of the three is told apart by colour alone. An AI message's card also has a dashed border, and each message is an `article` named for screen readers as "AI message from AI assistant" or "Agent message from <name>": that is 6.8, built with the thread in Phase 3. A draft an agent approved (6.2) is saved as that agent's message and labelled Agent, not AI, since approving it made it their reply. Status and category are selects rather than badges: they set what they report, sending only the field that changed, and the API answers with the whole ticket, which goes straight into the detail cache while the lists are invalidated — where a changed ticket now sorts is the API's to decide. An unclassified ticket shows `unclassified` as a placeholder, not an option, because the API classifies a ticket but takes nothing back. The escalation badge names its reason beside a Clear button. An Assignee select offers Unassigned and every active user, with an Assign to me shortcut that steps aside once the ticket is the viewer's; a ticket whose assignee is missing from the list — deactivated since, or the list still loading — still names them. Renaming, creating or deactivating a user refreshes the choices and the ticket caches, since a deactivation takes the user's tickets away. A refused change shows beside the controls, which keep the value the API stored rather than the one that was clicked. Under the thread sits the reply box, validated by the API's own `createReplySchema` so a blank or over-long reply never becomes a bare 400. It empties only on success: a reply the API refused stays where its author can try again rather than write it twice. The API answers with the stored message, which joins the cached thread at once, and the ticket is refetched because the reply moved the last-activity stamp the lists sort on. Its hint says the reply is saved on the ticket, since emailing it arrives in Phase 4. A malformed id is judged by the API's own `ticketIdSchema`, so `/tickets/abc` is the same Ticket not found as a missing one and sends no request that could only 404 |
| UI | Tailwind CSS 4 (via `@tailwindcss/vite`) + shadcn/ui (radix base, nova preset); components in `src/components/ui`, imported through the `@/` alias |
| Forms | react-hook-form with `zodResolver`; shadcn `Field`/`FieldError`, `noValidate` so the schema's messages replace the browser's. A rejected request stays a form-level alert — marking a field would disclose which one the API refused to name |
| Linting | oxlint |
| API calls | `apiRequest` in `src/lib/api.ts` over an axios instance — `baseURL` from `VITE_API_URL`, `withCredentials: true`, and a response interceptor turning any HTTP failure into `ApiError`. A request that got no response at all is left alone, so the query client retries a dropped connection where it would not retry a 401 |
| Axios adapter | `adapter: 'fetch'` rather than the default xhr. It is what runs where the app ships, and it keeps one seam — global `fetch` — for the tests to stand in front of, instead of an XMLHttpRequest happy-dom would put on the wire for real |
| Local development | Vite dev server proxies `/api` to `http://localhost:3000` |
| Route protection | `RequireAuth` wraps every route but `/login`; `GET /api/auth/me` on load, 401 redirects to `/login`. `RequireAdmin` nests inside it around admin-only routes and sends a non-admin to `/` — signed in, so `/login` would name the wrong problem. `AppLayout` drops admin-only nav items for agents. All three are convenience, not a boundary; Express refuses the request either way |
| Session ended mid-use | Any 401 from any query or mutation — not only `/auth/me` — sets the cached current user to `null`, which `RequireAuth` turns into `/login`, and drops every other cached query as belonging to the ended session. Handled once, on the `QueryCache` and `MutationCache` in `query-client.ts`. There is no push channel, so a deactivated user finds out only when their browser next makes a request that needs the session. Today that is their next page load: no agent screen fetches anything but the session check, which is cached for 30 seconds, and the dashboard's health check is unauthenticated. From Phase 3 the ticket screens' requests make it any navigation. Signing in clears the whole cache too: a session that simply expired is reported by `/auth/me` as `null`, not a 401, so nothing else would clear what it left behind |

Hiding screens in the UI is not access control. Express enforces permissions on every endpoint.

## Backend (`apps/api`)

| Concern | Choice |
|---|---|
| Runtime | Bun (runs TypeScript directly; no build step) |
| Framework | Express 5 + TypeScript |
| Validation | Zod 4 |
| Environment config | `apps/api/src/env.ts` validates `process.env` at import; invalid or missing variables print the problem and exit 1. `NODE_ENV` and `WEB_ORIGIN` carry no defaults on purpose — both decide how tightly the API is locked down, so a deploy that forgets one must fail to boot rather than quietly serve an insecure default. `ADMIN_EMAIL` / `ADMIN_PASSWORD` are seed-only and validated in `prisma/seed.ts` instead, so the API can start without them |
| ORM | Prisma |
| Database | PostgreSQL |
| Local database | `docker compose up -d --wait` at the repo root starts Postgres 18 on `localhost:5432` (user, password, and database `helpdesk`); copy `apps/api/.env.example` to `apps/api/.env` |
| Background jobs | pg-boss 12, running inside the API process (Koyeb's free instance cannot run a separate worker). `createBoss` in `apps/api/src/jobs/boss.ts`: its own `pgboss` schema in the same database, created on start (Prisma migrates `public` only); a pool of 3 beside Prisma's, labelled `helpdesk-jobs`; an `error` listener, since an unhandled one would crash the process. `src/index.ts` starts it before the API listens and stops it gracefully on SIGTERM, giving a running job 10 seconds. Verified on Bun 1.4.2, with Prisma's `?schema=public` left on the connection string. Queues: `process-ticket` (`apps/api/src/jobs/process-ticket.ts`), created on start; a job carries `{ ticketId, messageId }`, ids only, and is queued inside the transaction that saves the inbound message, through pg-boss's `fromPrisma` adapter, so the two commit or roll back together. Queued separately, a failure between them would leave a message no job picks up, and Resend's redelivery would be dropped as a duplicate. `createApp` takes the queue from `src/index.ts` and has no default: without one, an inbound email fails with a 500 and is redelivered |
| Scheduled tasks | GitHub Actions scheduled workflow calls protected endpoints (the API sleeps when idle, so in-process schedules are unreliable). The workflow itself is 8.11. The endpoints are under `/api/tasks` (`apps/api/src/routes/tasks.ts`), with no session: the caller sends `Authorization: Bearer <TASKS_SECRET>`, required at boot and at least 32 characters. Both sides are SHA-256 hashed and compared with `timingSafeEqual`, so neither the secret nor its length leaks through timing; every refusal is the same 401, and a signed-in admin is refused too. `POST /api/tasks/auto-close` (5.16) sets every Resolved ticket whose `autoCloseAt` has passed to Closed through `statusChange`, in one `updateMany` whose condition is the status and the timer, so a ticket reopened or given a fresh timer meanwhile is left alone; it answers `{ closed: n }` and is safe to repeat. `POST /api/tasks/cleanup-sessions` (5.16a) deletes expired sessions and answers `{ deleted: n }` |
| CORS | `cors` package, single origin from `WEB_ORIGIN` (`https://app.<domain>` in production, `http://localhost:5173` locally), `credentials: true` |
| Error handling | A body-parser failure answers its own status (400 unparseable, 413 over the 100KB default) and logs only the error type. The error object is never logged for a client error: `express.json()` attaches the raw body, which for a truncated login POST means a cleartext password in the log |
| End-to-end tests | Playwright in `apps/e2e`, Chromium. Starts its own API on 3100 and web server on 5273 against a third database, `helpdesk_e2e`, so a run cannot reach the development servers or their data. `bun run test:e2e` prepares the database before Playwright starts, because Playwright launches `webServer` ahead of `globalSetup` |
| Tests | `bun test` + Supertest (`apps/api/test`) against a real `helpdesk_test` database (`.env.test`, loaded automatically because `bun test` sets `NODE_ENV=test`); `bun run test` applies migrations first and truncates between tests. The web app uses `bun test` with happy-dom and Testing Library |

## Authentication

Database sessions.

| Piece | Design |
|---|---|
| Session table | Prisma `Session` model: `id`, `tokenHash`, `userId`, `expiresAt`, `createdAt` |
| Token | 32 random bytes (`crypto.randomBytes`); raw token in the cookie, SHA-256 hash in the database |
| Cookie | `httpOnly`, `Secure`, `SameSite=Lax`, set by `api.<domain>` |
| Passwords | `Bun.password` (argon2id, m=65536 KiB, t=2, p=1); no argon2 or bcrypt dependency |
| Expiry | 8 hours; expired sessions deleted by a scheduled task, `POST /api/tasks/cleanup-sessions` (5.16a). `requireAuth` already refuses them, so the cleanup only removes dead rows. Expired means `expiresAt` at or before now, the same test `requireAuth` applies |
| Login | `POST /api/auth/login` creates a session and sets the cookie |
| Login timing | Always one argon2 verification, against a dummy hash when no account matches. Short-circuiting would answer an unknown address ~60x faster than a real one, which enumerates accounts however uniform the response body is |
| Login rate limit | `express-rate-limit`, 10 attempts per 15 minutes, keyed by IP *and* submitted address so one target cannot exhaust another's budget. Counts successes too. **Production only** — it guards an endpoint facing the internet, and locally would only throttle whoever is building the screens that sign in. Safe to gate on `NODE_ENV` because it has no default, so a deploy that omits it refuses to boot. Needs `trust proxy` set once the API sits behind Koyeb's proxy (task 8.5) |
| Logout | `POST /api/auth/logout` deletes the session and clears the cookie |
| Current user | `GET /api/auth/me` returns `{ id, email, name, role }` or 401 |
| Request middleware | Hash cookie token, load session + user, reject if missing, expired, or user deactivated |
| Deactivating an agent | Mark user inactive, delete all their sessions, and unassign their tickets |
| First admin | `bun run db:seed` upserts on email using `ADMIN_EMAIL` / `ADMIN_PASSWORD`; re-running never resets the password, but does mark that admin protected and active again, which recovers them if they were switched off by hand |
| Agent creation | `POST /api/users`, admin only |

## User Management

| Concern | Choice |
|---|---|
| Routes | `apps/api/src/routes/users.ts`, mounted at `/api/users`. `requireAuth` and `requireAdmin` are applied to the router, not to each route, so a route added later cannot be left unguarded by omission |
| List response | `GET /api/users` returns every user — active and deactivated — as `{ id, email, name, role, isActive, createdAt }`, oldest first with `id` breaking ties. The `UserSummary` type in `@helpdesk/shared` is the contract |
| Field selection | An explicit Prisma `select`, never an `omit` of `passwordHash`: a column added to `User` later is then absent from the response until someone chooses to expose it |
| Creating an agent | `POST /api/users` takes `{ email, name, password }` and answers 201 with a `UserSummary`. `role` is fixed to `agent` in code and never read from the body, so one stolen admin session cannot mint a second admin. Password minimum 12, matching `ADMIN_PASSWORD` in the seed, capped at 200 so a 100KB body never reaches argon2. Email capped at 254, the longest address SMTP delivers to — uncapped, a few KB overflowed the unique index's 2704-byte row limit and became a 500 after argon2 had run |
| Duplicate address | The unique index decides, not a `findUnique` first: the `P2002` violation is mapped to 409. Check-then-insert would let two concurrent requests both pass the check and turn one into a 500. Addresses are lowercased before the insert, because login looks them up lowercased — a row stored with capitals would be an account nobody could sign in to |
| Editing a user | `PATCH /api/users/:id` takes any of `name`, `email`, `password`, `isActive`, at least one, under the same field schemas as create. A taken email is 409 and nothing in the request lands. Setting a password deletes that user's sessions — it is usually reset because it leaked or was forgotten — except the session an admin changes their own from. Argon2 runs before the transaction, so it never holds one open |
| Deactivating and reactivating | Deactivation flips the flag and deletes the user's sessions in one transaction, so the rows cannot outlive the flag. `requireAuth` refusing an inactive user is what actually locks them out; deleting the sessions is what stops a later reactivation handing back tokens that were live weeks ago — reactivation restores the account, never a session. Reactivating someone who *was* inactive deletes their sessions too: a login that read them as active before a deactivation committed inserts its session after the delete, and reactivation would otherwise bring it to life. An already active user is left alone. Deactivation also returns the user's tickets to nobody in the same transaction; each one's `updatedAt` moves, so they rise in a list sorted by activity, where someone will pick them up. Reactivation does not hand them back — whoever took them since may be working them |
| Who may change whom | One pure function, `authorise()` in `@helpdesk/shared`, used by the API and the page alike. The seeded admin may edit anyone and deactivate anyone but themselves. Any other admin may edit their own details and edit or deactivate agents, and touch no other admin (403). Nobody deactivates themselves or the seeded admin (409). Only the seeded admin reaching other admins means two admins can never deactivate each other at once, and none can lock another out by changing their email or password |
| The seeded admin | `User.isProtected`, set by the seed. The API cannot recognise that admin by `ADMIN_EMAIL`, which stays seed-only, hence the column. `/auth/me` does not carry it; the users page reads the viewer's own row in the list |
| User-management write limit | `POST` and `PATCH /api/users` share 60 writes per 15 minutes, keyed by the admin's id. Every create pays argon2 at 64 MiB before the unique index is asked, so a scripted or stolen admin session could otherwise keep the API hashing. **Production only**, like the login limit: the end-to-end suite creates and deactivates users constantly |
| Unknown user | 404 for an id with no row (Prisma `P2025`) and for a malformed id alike — neither names a user. The uuid check only answers early: `User.id` is `TEXT`, so a malformed id would reach Postgres and simply miss |

## Tickets

| Concern | Rule |
|---|---|
| Statuses | Open, Resolved, Closed |
| Categories | General question, Technical question, Refund request |
| Resolved | Issue is solved. Set by the AI or an agent. |
| Closed | Ticket is no longer open. Set by an agent or by auto-close. |
| Auto-close | A Resolved ticket closes 14 days after it was resolved. Open and Closed tickets have no timer. |
| Setting a status | Always through `statusChange()` in `apps/api/src/tickets/status.ts`, which returns the status with its `autoCloseAt`: now + 14 days for Resolved, null otherwise. Setting Resolved again restarts the timer. A change that does not set a status leaves the timer alone. |
| Timer reset | A student message on a Resolved ticket restarts the 14-day timer. |
| Student reply to Resolved or Closed | Status does not change. AI processes the new message: replies and updates category and summary. |
| Escalation | Ticket flagged `needsAgent` with a reason: `refund_approval`, `ai_failed`, `unverified_sender` (the first email did not pass DMARC) `auto_reply_limit` (the AI has emailed as much as it may; #239) or `agent_assigned` (an agent is on the ticket, so the AI's reply waits for them; 6.9) |
| Assignment | `Ticket.assigneeId`, nullable: at most one agent or admin is responsible for a ticket, or nobody. A label, not a permission — anyone can still reply or change status. `onDelete: SetNull` rather than `Message.agentId`'s Restrict, because an assignment is not a record worth keeping a user row for. Indexed, unlike the list's other filter columns, because it is a foreign key read from both ends: the assignee filter, and the SET NULL a user delete runs. Set through `PATCH /api/tickets/:id`, and cleared when the assignee is deactivated |
| Listing tickets | `GET /api/tickets` for any signed-in agent or admin: `status` and `category` filters, an `assignee` filter taking `me` (read from the session, so a link means the same for whoever opens it) or `none`, a `needsAgent` filter taking `true` or `false` (6.4; kept as text in the shared schema, since the page parses its URL with it and sends the result back, and not `z.coerce.boolean`, which reads "false" as true), `sort` (createdAt/updatedAt) and `order`, `page` and `pageSize` (20 by default, 100 at most). `id` breaks ties in the sort direction, so tickets sharing a timestamp cannot move between pages. Answers `{ tickets, page, pageSize, total }`, each ticket naming its assignee by id and name or `null`; one 400 for any invalid query. No indexes yet — at a few hundred tickets a sequential scan beats one |
| Reading a ticket | `GET /api/tickets/:id` answers the ticket with its thread, oldest message first, each message naming its agent, and the ticket its assignee, by id and name only. `emailMessageId` stays out: it is threading plumbing, not something a screen shows. A malformed or unknown id is the same 404 |
| Changing a ticket | `PATCH /api/tickets/:id` takes any of `status`, `category`, `needsAgent` and `assigneeId`, at least one. `needsAgent` accepts only `false` — agents clear an escalation, they do not raise one — and clearing it clears `escalationReason`. `assigneeId` is a user's UUID, or `null` to leave the ticket with nobody; a user who does not exist and one who is deactivated get the same 400, `Assign the ticket to an active user`, since either way there is nobody to hand it to. The check and the update are one transaction, and the check takes the user row `FOR UPDATE` — the app's only raw SQL, since Prisma cannot ask for the lock. Unlocked, a deactivation committing between them had already cleared that user's tickets, so the assignment landed afterwards and parked the ticket with someone who could not sign in and whom neither assignee filter matched; a plain transaction does not help, because at READ COMMITTED the unlocked read still sees the row as active. Anything else in the body is stripped, so a change of nothing is a 400. Answers the same detail shape as the GET |
| Who can be assigned | `GET /api/tickets/assignees` answers every active agent and admin as `{ id, name }`, by name with `id` breaking ties — the same users `PATCH` accepts. On the tickets router rather than `/api/users`, which is admin only and carries whole user rows, because an agent assigning a ticket needs the names too |
| Agent replies | `POST /api/tickets/:id/replies` emails the reply to the student, then saves it as an outbound `agent` message attributed to the session's user, whatever the body claims. Emailed first, threaded onto the student's emails (the first and the latest 20, so References stays bounded however long the ticket; `sendEmail` also drops any ID failing the Message-ID rule before building headers) with subject `Re: <subject>`: a refused send answers 502 and saves nothing, so a reply in the thread is one the student was sent. Never emailed to an RFC 2606 reserved domain (`.test`, `.example`, `.invalid`, `.localhost`, `example.com/.net/.org`), where the seeded and end-to-end students live; those replies are saved without a send. The saved message has no Message-ID, since Amazon SES sets its own and does not report it. Body 1–10,000 characters trimmed; the ticket's `updatedAt` moves in the same transaction, so a replied-to ticket rises in a list sorted by activity, and its status is left alone |
| Ticket write limit | `POST /api/tickets/:id/replies` and `PATCH /api/tickets/:id` share 120 writes per 15 minutes on one budget, keyed by the acting user's id behind `requireAuth` and enforced in production only, so the end-to-end suite works freely. One budget because both are the same agent on the same queue: a reply can carry 10,000 characters into a thread that is read back whole, and since the assignment lock a change costs a locked read and a write. Higher than the user-management limit — answering tickets is the job, and a busy agent should never meet it |
| Sample data | `bun --filter '@helpdesk/api' db:seed:dev` writes eight tickets covering every status, category and escalation reason, with student, AI and agent messages. A separate script from `db:seed`, which also runs in production, and it refuses any `NODE_ENV` but `development`. Sample students are on `student.example` (reserved, undeliverable); a re-run replaces those tickets and touches no others. Agent replies are authored by the seeded admin, so run `db:seed` first |

## Email

| Concern | Choice |
|---|---|
| Provider | Resend (free tier includes receiving) |
| Inbound | Resend receiving webhook → Express creates or updates ticket and queues a job |
| Webhook verification | `POST /api/webhooks/resend`, no session: Resend proves itself by signature. `resend.webhooks.verify` (Standard Webhooks: HMAC-SHA256 over id, timestamp and body, keyed by `RESEND_WEBHOOK_SECRET`, required at boot) checks the `svix-*` headers and refuses a stale timestamp, so a captured request cannot be replayed. Mounted ahead of `express.json()` and read as raw text whatever the Content-Type, because the signature covers the exact bytes. Anything that fails is 401, logged by reason only, never payload. The event carries metadata only (sender, subject, `message_id`, `email_id`); the body is fetched separately |
| Inbound parsing | `parseInboundEmail` in `apps/api/src/email/inbound.ts` reduces a received email (from `resend.emails.receiving.get`, which needs a Full access key) to sender address and display name, subject, plain text, Message-ID, In-Reply-To and References. Resend gives References as a JSON array string when it holds several IDs and bare when one, so the bracketed IDs are picked out, which also reads the raw space-separated form. The display name comes from the From header; the top-level `from` is the bare address. The text keeps quoted history; an email with no plain-text part gives empty text |
| Inbound bounds | `inboundTicketFields` in `apps/api/src/email/inbound-fields.ts` is what an inbound email may write, since the columns are unbounded `TEXT` (Phase 3 security review, #164). Returns null, refusing the email, only for a sender that fails `emailField` (malformed or over 254): no reply could reach it. Everything else is cut down, never refused, so a student's message is not dropped over something cosmetic: subject to 200 ending in "…" or "(no subject)"; a name over 100 dropped; text to 20,000 keeping its beginning, where the new words are, then "[Message shortened]", or a placeholder when empty. The inbound text cap is twice an agent reply's because it carries quoted history. Lengths count code points, so a cut never splits an emoji. The Message-ID must pass one rule (`isStorableMessageId` in `apps/api/src/email/message-id.ts`): a single `<…>` token with no whitespace, quotes or control characters, at most 250 characters. It is copied into our replies' `In-Reply-To`/`References`, so a CR/LF could inject a header; and 250 non-ASCII characters are at most 750 bytes, inside btree's 2704-byte index row, where the earlier 998 cap let a 3008-byte ID fail the unique index on every redelivery (Phase 4 security review, #210). Anything failing it is stored as none, never as an empty string, which the unique column would treat as one ID shared by every email lacking one. NUL is stripped from subject, name and text, since Postgres refuses it in `text`; a missing Subject or Message-ID is read as empty |
| Inbound save | The webhook fetches a verified `email.received` event's email (`fetchReceivedEmail`, injected through `createApp` like the sender), parses and bounds it, and `ingestInboundEmail` appends it to the ticket it replies to, or else saves it as a new Open ticket with its first message, in one insert. A Message-ID already stored is a duplicate (task 4.6); two deliveries racing past that check are settled by the unique index (P2002), and since ticket and message are one insert the loser leaves no empty ticket. Duplicates, refused senders and other event types are acknowledged (204) so Resend stops redelivering; a failed fetch answers 502 and a database failure 500, so Resend tries again. Logs the Resend email id and outcome only |
| Threading | A reply is matched (task 4.8) through its `In-Reply-To`, then `References` newest to oldest, against the Message-IDs stored on inbound messages. `References` is what matches in practice: our replies' Message-ID is set by Amazon SES and never reported, so a student's `In-Reply-To` names one we do not have, while `References` still carries the student's own earlier IDs (verified for Gmail). Capped at 100 IDs, always keeping the first reference, the student's opening email, which RFC 5322 has clients keep when they trim. Only the ticket's own student can add to it (address compared ignoring case): anyone copied on a thread has seen its IDs. And only after a DMARC pass (task 5.2a, `passedDmarc` in `inbound.ts`), since that address check is only as good as a From anyone can forge: Resend's receiving (Amazon SES) adds `Authentication-Results` stamped `amazonses.com`, and every `dmarc=` result in those must be `pass`, so neither a header the sender forges nor a pass planted in a field SES copies (such as the HELO name) outvotes SES's real verdict. Anything else, a fail, `none` from a domain with no DMARC policy, or no header, opens a new ticket rather than joining one; nothing is dropped. When IDs reach two tickets, the nearest wins. The reply adds a message and moves `updatedAt`; subject and status stay, whatever the status (task 4.9): a student writing back to a Resolved or Closed ticket has not reopened it. On a Resolved ticket `autoCloseAt` starts over at now + 14 days, so it does not close while the student is still writing; the status is that update's own condition (`updateMany … where status = resolved`), so an agent changing it at the same moment leaves no stray timer. No match, or another sender, starts a new ticket |
| New-ticket cap | 4 new tickets per sender per rolling hour (task 5.2b, `ingest.ts`): each costs a Resend fetch and, once the AI answers it, an Anthropic call, and nothing else limited inbound volume. Past it the email is acknowledged (204) and saves nothing, so Resend does not redeliver it. Only new tickets count, including a reply that opens one because it did not pass DMARC; a reply joining an existing ticket is never capped. Counted from the tickets table (sender ignoring case, `createdAt` in the last hour), no separate store; the count and insert are not one step, so emails arriving together can pass it by one or two. Keyed on the sender, not an IP limit on the webhook, since every real webhook call comes from Resend. It does not stop someone rotating forged senders; only a global cap would |
| Automated email | Before anything is saved, `isAutomatedEmail` (task 4.7) drops mail a machine sent: `Auto-Submitted` with any value but `no` (RFC 3834: auto-replied, auto-generated, auto-notified, parameters allowed), any `X-Autoreply`, or a sender whose local part is `mailer-daemon` or `postmaster` (the RFC 3464 bounce senders). Acknowledged with 204, no ticket. Otherwise an agent's reply to a student on holiday would come back as a new ticket, and once the AI answers tickets two autoresponders could answer each other without end. `Precedence: bulk` is not used: mailing lists set it on mail people write |
| Local inbound testing | A Cloudflare quick tunnel (task 4.10): `cloudflared tunnel --url http://localhost:3000` prints a random `https://….trycloudflare.com` address that forwards to the local API, with no Cloudflare login (not supported while `~/.cloudflared/config.yaml` exists). In Resend, add a webhook endpoint at `<address>/api/webhooks/resend` for `email.received` only, put its signing secret in `apps/api/.env` as `RESEND_WEBHOOK_SECRET`, and restart the API. The address changes on every start, so the endpoint lasts one session: disable it in Resend when the tunnel stops, or Resend keeps retrying a dead address. Verified 2026-09-25: a new Gmail email opened a ticket, and a Gmail reply to an SES-sent agent email joined its ticket through `References` |
| Outbound | Resend SDK, plain text, through `sendEmail` in `apps/api/src/email/outbound.ts`. Sets `In-Reply-To` to the parent and `References` to the whole chain so replies stay in the student's thread. Sets no `Message-ID`: Resend sends through Amazon SES, which replaced one the API set with its own (seen in a delivered email's headers), and the send response returns only Resend's id. A student's reply is therefore matched to its ticket by `References`, which carries the student's original Message-ID, not by the Message-ID of our reply. `RESEND_API_KEY` and `EMAIL_FROM` are required at boot. An email marked `automatic` (the AI's replies) carries `Auto-Submitted: auto-replied` (RFC 3834, #239), which auto-responders read as "do not answer", so two of them cannot loop through the helpdesk |
| Domain | `helpdesk.mahjoub.io`, one Resend domain for sending and receiving, in region `ap-northeast-1`. A subdomain because Resend receives every address on a domain whose MX points at it, so the root `mahjoub.io` stays free for a personal inbox |
| Address | `support@helpdesk.mahjoub.io`. Resend registers no individual addresses: the local part is whatever `from` says when sending, and any address on the domain reaches the webhook when receiving |
| DNS | Cloudflare, all records DNS only: a proxied CNAME fails Resend's verification, and MX records cannot be proxied |

Free tier limits (from search results, not verified on Resend's pricing page): 3,000 emails/month and 100/day, shared between sent and received.

## AI

| Concern | Choice |
|---|---|
| Model | `claude-haiku-4-5` via the Anthropic TypeScript SDK, pinned in `apps/api/src/ai/client.ts` — one model for classification, summary and reply, so the evaluation set in 5.18 measures one thing. Chosen on measurement over Sonnet 5 and Opus 5 against this knowledge base: ~2.9s and ~$2.23 per thousand tickets, against ~3.7s / $5.02 and ~5.2s / $15.36. Haiku takes no `effort` parameter and does no adaptive thinking, which is most of the difference. The cost is judgement — on a technical complaint ending "just refund me" it answered `technical` where Opus answered `refund`, which the keyword safeguard below has to catch |
| Key | `ANTHROPIC_API_KEY`, validated by `env.ts` at boot like the Resend keys, so a missing or malformed key fails the deploy rather than a job at 3am. It must be **workspace-scoped**: an organisation-level key is refused with a 400 asking for an `anthropic-workspace-id` header. Set the monthly spend limit on that workspace (8.13) |
| Checking the key | `bun --filter '@helpdesk/api' ai:ping` makes one small real call and prints the model, stop reason, tokens and latency. By hand only: it costs money and needs the network, which is why nothing in `bun test` reaches the API |
| Call | One call per new inbound message, returning category, summary, and reply draft as structured JSON |
| Output shape | `aiOutputSchema` in `packages/shared/src/ai-output.ts`: category, a summary capped at 300 characters because it is one line on the ticket list, and a reply under the same 10,000-character ceiling an agent's reply has. `aiOutputJsonSchema` is derived from it with `z.toJSONSchema`, so what the prompt asks the model for and what the job will accept cannot drift. Parsing strips an unexpected field rather than failing the job over a key nobody reads |
| Prompt | `apps/api/src/ai/prompt.ts`. The system prompt is the instructions and the knowledge base, identical on every call; everything ticket-specific is the user message, the thread oldest first with each message labelled by who wrote it. A refund request is stated to win over every other category, since a technical complaint ending "just refund me" is what the cheaper model missed before that line existed. Replies come only from the knowledge base and never approve, refuse or price a refund. Output is `messages.create` with `zodOutputFormat(aiOutputSchema)` as the format; the answer is checked against the same schema after the stop reason, so the request and the check are one definition |
| Untrusted email | The ticket sits in `<ticket>` tags the model is told to treat as data, and a body cannot close them — `</ticket>` inside an email is neutralised before it reaches the prompt. The eight-sample run included an injection asking for a $500 refund; it was classified refund and the reply only said the request goes to the team |
| Prompt caching | Marked on the system prompt, and **inert today**: Haiku 4.5 caches nothing under 4,096 tokens, and a call is about 1,770. It costs nothing to place and starts saving once the knowledge base grows past the minimum; `usage.cache_read_input_tokens` staying 0 is expected until then |
| Usage logging | One line per model call (5.17, `usageLine` in `apps/api/src/ai/usage.ts`), e.g. `AI usage: ticket=12 outcome=reply input=1770 output=110 cache_read=0 cache_write=0`. `cache_read` is the prompt-cache hits, `cache_write` the calls that primed the cache; null from the SDK is logged as 0 so every line has the same fields. `outcome` is `reply`, `refund_draft`, or `failed_<reason>` for a refused or cut-off answer, which is billed too; `forced_by=<n>` is added when the refund safeguard overruled the model. Logged once the call returns, before anything is saved. A failure that never reached the model (rate limit, outage) costs nothing and logs no usage line. Never the student's email or the reply: the ticket id finds them |
| Evaluation set | Sample emails in `apps/api/eval/samples.ts` (5.18), written from `knowledge-base-brief.md` with the category the brief gives each: 14 general, 6 technical, 9 refund, the ninth an injection trying to get a promise of money sent with no refund word in it (#239). The brief decides where it and the prompt disagree. `bun run ai:eval` (`scripts/ai-eval.ts`, scoring in `src/ai/evaluate.ts`) runs them one at a time against the real API and reports the model's accuracy, the accuracy after the refund safeguard, a per-category breakdown, the safeguard's overrides, and the cost. **Billed, about $0.07 a run**, so by hand only; `test/evaluate.test.ts` checks the scoring against a stand-in client. Baseline, 2026-09-30: model 22/28 (79%), after the safeguard 23/28 (82%). The misses are the prompt's: logins and an account-security worry went technical, since the prompt lists logging in under technical and the brief under general; both download questions went general, since the prompt's technical is "something is not working" and the brief files downloads under technical; and "charged full price, send me the difference" went general, caught by neither the model nor the safeguard's phrase list. After 5.19 aligned the prompt's categories with the brief and widened the phrase list, 2026-09-30: model 27/28 (96%), after the safeguard 28/28 (100%), $0.067 |
| Checking the prompt | `bun --filter '@helpdesk/api' ai:samples` runs eight sample emails — two per category, the refund trap, and an injection — against the real API. By hand only; about $0.02 a run |
| Knowledge base | Markdown files in a cached system prompt; no vector database. One file per topic students write about, in `apps/api/knowledge-base/` beside the API that loads it (task 5.5, `loadKnowledgeBase` in `apps/api/src/ai/knowledge-base.ts`: files in name order so the cached prefix never changes, each wrapped in `<article file category>`, and a missing or wrong `category:` line throws rather than loading) and inside the API's Docker build context. Each opens with a `category:` frontmatter line (general, technical or refund) and holds short Q&A articles. Written from `knowledge-base-brief.md` (task 5.4): every answer line is the brief's own wording, and the brief's routing table stays out, since it instructs the AI rather than informs the student and belongs in the prompt (task 5.8) |
| General / technical questions | The reply is emailed, threaded as an agent's is, then saved as an `ai` message, and the ticket set Resolved through `statusChange` so the auto-close timer starts. Emailed before it is saved, as 4.3 does for agents: a failed send saves nothing and the job retries, so the thread never shows a reply the student did not get. The cost is a narrow window — the email sent, then the save failing — in which a retry emails the student twice. Only an Open ticket is resolved: a follow-up on a Resolved or Closed one gets its reply and a new category and summary, but keeps its status and timer (5.14). The status is the update's own condition, not read with the thread, so an agent closing the ticket while the model answers is not undone |
| Refund requests | By the model's category or the safeguard's: the reply is saved as a pending `ReplyDraft` and the ticket flagged `needsAgent` with `refund_approval`, in one transaction, and nothing is emailed. Status is never changed: an Open ticket stays Open, since nobody has answered the student, and a Resolved or Closed one keeps its status (5.14). One pending draft per ticket: a follow-up while one waits replaces its body, and a reviewed draft is never touched |
| Reply drafts | `ReplyDraft`: the ticket, the body, `status` (`pending` by default, then `approved` or `rejected`), and `reviewedById` / `reviewedAt`, both null while pending. Deleted with its ticket. `Restrict` on the reviewer, as on `Message.agentId`: an approval is the record of who let a refund reply go out. Nothing yet enforces one pending draft per ticket, or that a reviewer is set exactly when the status is not pending; both are for the code that writes drafts (5.13) and reviews them (6.2, 6.3) |
| Draft list | `GET /api/drafts?status=pending|approved|rejected` (6.1, `apps/api/src/routes/drafts.ts`), for any signed-in agent or admin. `status` is required, so a list never mixes drafts waiting on someone with drafts dealt with; anything else is 400. Each draft carries its ticket's id, subject, student, category, escalation reason and `senderVerified`, so a reviewer sees before approving that an unverified sender's address may be forged (#239). The reviewer is named by id and name only. Pending drafts come oldest first, so the longest wait is at the top; reviewed ones most recently reviewed first. Capped at 100, unpaginated: one pending draft per ticket keeps the queue short |
| Approving a draft | `POST /api/drafts/:id/approve` (6.2), any signed-in agent or admin, under the ticket-write rate limit. An optional `body` is the agent's edit, held to an agent reply's rules (trimmed, 1–10,000 characters); without one the draft goes as the AI wrote it. **Claimed before it is sent**: one `updateMany` moves it from pending to approved with the reviewer and time, so of two agents approving at once only one gets past it (the other gets 409) and the student is emailed once. A failed send (502) puts it back to pending, edit kept, conditional on that claim. The cost of this order is a crash between claim and send, leaving a draft marked approved that was never emailed; the other order's cost, the reply sent twice, is the one a student sees. Sent threaded like an agent's reply and not marked `Auto-Submitted`, since a person approved it. Then, in one transaction, it is saved as the approver's own `agent` message, the ticket's `needsAgent` and reason are cleared, and an Open ticket is resolved through `statusChange` (a Resolved or Closed one keeps its status). Already reviewed is 409; unknown or malformed id 404 |
| Rejecting a draft | `POST /api/drafts/:id/reject` (6.3), any signed-in agent or admin, under the ticket-write rate limit, no body. One conditional `updateMany` moves it from pending to rejected with the reviewer and time, so a draft approved and rejected at once ends one or the other; already reviewed is 409, unknown or malformed id 404. Nothing is emailed, and the draft stays as the record of what the AI proposed and who turned it down. **The ticket is left as it is**: Open stays Open, since the student has not been answered, and `needsAgent` with its reason stays, so the ticket remains in front of agents until one replies, and a `refund_approval` reason keeps the AI from answering its follow-ups (#239) |
| Draft review panel | On ticket detail, between the thread and the reply box (6.6, `apps/web/src/components/draft-review.tsx`), so the agent reviews with the conversation in view. `GET /api/tickets/:id` carries `pendingDraft` (id, body, created) and `senderVerified`; there is no per-ticket drafts endpoint. The draft sits in an editable box under an "AI · Draft reply awaiting review" heading that says nothing has been sent; **Approve and send** posts the box's text (the shared `approveDraftSchema` made required, so an emptied box is refused rather than falling back to the AI's original), **Reject** posts nothing else. An unverified sender gets a warning before anyone approves (#239). Afterwards the ticket and the lists are refetched rather than patched, since approval adds a message, clears the escalation and may resolve the ticket. The announcement lives outside the panel, so it is still there once the panel goes. A failure keeps the draft and the edit, with the API's message |
| Refund safeguard | `decideRouting` in `apps/api/src/ai/refund-safeguard.ts`: a keyword check on the subject, every student message in the thread, and the drafted reply. Any phrase for money back — refund and its forms, money back, chargeback, reimburse, charged or paid twice, cancel my purchase, dispute the charge or dispute it with my bank, and partial money back (overcharged, charged the full price, send me the difference; 5.19) — overrides the model's category to refund and routes the ticket to an agent. Deliberately broad, and negation is not parsed: a false match costs an agent reviewing a draft, a miss lets the AI answer a refund request unapproved. Once a thread mentions money back, its follow-ups stay with agents. The decision carries the route for 5.13 and the phrases that forced it for 5.17 and 5.18 to count. A sum of money in the drafted reply (a currency sign before a number, or a number before a currency name) also routes to an agent (#239): the prompt forbids amounts, so one means the model was talked into it or misread the ticket |
| Processing a ticket | The `process-ticket` worker in `apps/api/src/jobs/process-ticket.ts`, registered at boot beside the queue 5.2 fills. Per job: load the thread (newest first, capped at `MESSAGE_PAGE_SIZE` as the detail page is, then read oldest first), ask the model, save `category` and `summary`. It then routes the answer (see General / technical questions and Refund requests). A ticket deleted before or during the call is skipped, not retried. The knowledge base loads once at start, so a broken one stops the API booting. **Every inbound email is now one real call**, about $0.002 on Haiku. Retries are the next row's |
| AI limits and holds | From the Phase 5 security review (#239), in `apps/api/src/ai/limits.ts` and `process-ticket.ts`. Counted from existing rows, no counter table: each student message queues one job, so inbound messages stand for AI calls, and each AI email is an `ai` message. **Before the call:** past 5 student messages on the ticket or 500 overall in 24 hours, the model is not asked and the ticket escalates `ai_failed` (worst case about $5 a day). The thread is cut to the newest messages within 40,000 characters (about 10,000 tokens), since a message count bounds nothing when a message can be 20,000 characters. **After the call, the reply is held as a pending draft instead of emailed**, in this order: a refund, by the model or the safeguard, or a refund draft already waiting (`refund_approval`; the model may have caught a refund no keyword could, and answering the follow-up would resolve and in time auto-close the ticket with the draft unseen); a ticket whose first email did not pass DMARC (`Ticket.senderVerified`, set at creation, false by default: otherwise anyone could forge a `From:` and have the academy email a stranger a subject they wrote; `unverified_sender`); 3 AI emails on the ticket in 24 hours, or 50 overall in the hour (`auto_reply_limit`). Big providers pass DMARC, so the students who lose instant answers are mainly those on domains with no DMARC policy. The usage line's outcome is `reply`, `refund_draft` or `held_<reason>`, and a job that gives up logs the error's name and code, never its message, which for a Prisma validation error quotes the reply **Also held (6.9, #250):** a ticket already escalated `ai_failed` keeps that reason, and a ticket with an assignee is held as `agent_assigned`, after the unverified-sender check and before the send limits, so the AI never answers over an agent's head. **One answer per burst (6.10):** a job skips, logging `AI skipped: … reason=newer_message`, when a newer inbound message exists on its ticket, since that message's job answers the whole thread. Jobs run one at a time, so two messages sent together used to get two emails in turn; only one message is the newest, so this also holds with several workers. Ids rise with every insert, so they order arrival. **One pending draft (6.11):** a partial unique index, `ReplyDraft_one_pending_per_ticket` on `ticketId` where `status = 'pending'`, declared in the schema through Prisma's `partialIndexes` preview feature, so `migrate dev` knows it rather than dropping a hand-written one. `saveDraft` updates the pending draft (the status is the update's own condition, so a draft just reviewed is never rewritten) or creates one; when another job's insert wins, the index refuses this one with P2002, and the save runs once more as an update |
| Failed calls | One error type, `AiFailure` in `apps/api/src/ai/failure.ts`, with a `reason` and a `retryable` flag for the job to read. Not retried — the same ticket fails the same way and each try is billed: `refusal`, `truncated` (`max_tokens` or the context window), `unexpected_stop`, and `rejected` (a 4xx such as a bad key). Retried: `invalid_output` (not JSON, or outside the schema — structured output fixes the shape but only describes the lengths), `rate_limited` and `unavailable` (5xx, dropped connection, timeout). The stop reason is read before the text is parsed, which is why the call is `messages.create` rather than `messages.parse`: `parse` throws a bare error on a cut-off or refused answer, losing both the stop reason and the usage. Anything not from Anthropic surfaces as itself, since that is a bug rather than a model failure |
| Failure after retries | The `process-ticket` queue retries a failed job twice, about 1 and 2 minutes later (`retryDelay: 60` with backoff): the SDK has already retried within seconds, so what reaches the job is an outage to wait out. `createQueues` updates the queue as well as creating it, since creating one that exists is a no-op and each job copies the policy when queued. The worker, registered with `includeMetadata` for the retry count, throws for pg-boss to retry; on the last attempt, or on an `AiFailure` that is not `retryable` (so a refusal is billed once), it flags the ticket `needsAgent` with `ai_failed` and completes the job. The status is not touched, so an Open ticket stays Open. A failed send or any other error is retried and escalated the same way. A ticket already flagged keeps its reason, so a pending refund draft is not hidden behind `ai_failed`. Not covered: a job still running at pg-boss's 15-minute `expireInSeconds` is failed by its supervisor (`failJobsByTimeout`), which retries it as usual but, on the last attempt, marks it failed without the worker, so that ticket is not escalated |
| Billing | Anthropic API usage is billed separately from a Claude Pro subscription |

## Ticket Flow

1. Email arrives → Resend webhook → Express saves the message (new ticket as Open, or added to an existing ticket) and queues a job.
2. Background job calls Claude → category, summary, reply draft.
3. General or technical question → reply sent; ticket set to Resolved (unless Closed).
4. Refund request → draft saved; ticket flagged for an agent.
5. AI failure after retries → ticket flagged for an agent.

Not free: Anthropic API usage. The custom domain is already owned.

### Domains

Frontend and API must be subdomains of one custom domain so the session cookie works:

- `app.<domain>` → Vercel
- `api.<domain>` → Koyeb

Do not serve the app from `*.vercel.app` in production; the browser treats it as a different site and blocks the session cookie. Vercel preview deployments cannot log in; use them for UI review only.

### Free tier constraints

From search results, not verified on providers' pricing pages:

| Provider | Limit | Effect |
|---|---|---|
| Koyeb | One instance, 512 MB RAM, 0.1 vCPU; sleeps after 1 hour without traffic | First request after idle is slow; background jobs run only while awake |
| Neon | 0.5 GB storage, 100 compute-hours/month; sleeps when idle | Enough for a portfolio |
| Resend | 3,000 emails/month, 100/day (sent + received) | Enough for a demo |

### Pipelines

- **Frontend:** Vercel builds and deploys on push.
- **Backend:** GitHub Actions → build image → run `prisma migrate deploy` against Neon → deploy to Koyeb.
- **Scheduled tasks:** GitHub Actions workflow on a schedule calls `POST /api/tasks/auto-close` and `POST /api/tasks/cleanup-sessions`, protected by a shared secret.

When an API change and a frontend change ship together, deploy the backend first.
